# L2 - Detailed Requirements

Design reference: `docs/mocks/pages/home/` (states `default`, `invalid`, `sending`, `sent`, `error`).

## L2-001: Home page content
**Traces to:** L1-001

The page at `/` shall render, without signing in, a header with the Goodwork logo and a "Start a project" link; a hero with the heading "Software for people doing good work", the company description, the "Why it costs less" paragraph and the Christian-owned sentence; a "What we build" section with the "Web and mobile apps" and "Websites" cards; the contact section; and a footer with the copyright year, location and contact email as a `mailto:` link. Copy shall match the mock.

**Acceptance Criteria:**
1. Given an anonymous visitor, when they open `/`, then the page returns 200 and shows the header, hero, both service cards, the contact form and the footer.
2. Given the page has rendered, when the visitor reads the services, then exactly two cards are shown, titled "Web and mobile apps" and "Websites".
3. Given the page has rendered, when the visitor reads it, then no price figure is shown.
4. Given the footer, when the visitor activates the email address, then it is a `mailto:` link to the studio's contact address.
5. Given the page has rendered, when the document title is read, then it names Goodwork.

---

## L2-002: Start a project shortcut
**Traces to:** L1-001

**Acceptance Criteria:**
1. Given the home page, when the visitor activates "Start a project", then the page scrolls to the contact form and focus moves to the email field.
2. Given a keyboard user on the home page, when they press Tab first, then a "Skip to content" link is focused, and activating it moves focus to the main content.

---

## L2-003: Contact form fields
**Traces to:** L1-002

The form shall have exactly two required fields: "Email" (type email, autocomplete email) and "What are you working on?" (multi-line, with the help text "A sentence or two is plenty. Who you serve, what you need, and roughly when."), a "Send request" button and the line "We reply within two business days."

**Acceptance Criteria:**
1. Given the default state, when the visitor views the form, then it shows only the email and message fields, each labelled as required, and the "Send request" button.
2. Given the message field, when the visitor reads it, then its help text is programmatically associated with it.

---

## L2-004: Client-side validation
**Traces to:** L1-002

Validation runs on submit, then live per field once a field has shown an error. An email is valid when it is a complete address of at most 254 characters. A message is valid when it has at least one non-whitespace character and at most 2000 characters.

**Acceptance Criteria:**
1. Given both fields empty, when the visitor submits, then no request is sent, an error summary titled "Two things to fix before we can send this" appears and receives focus, and it links to each invalid field.
2. Given an email "ruth@" , when the visitor submits, then the email field shows "Enter a complete email address like name@organization.org" and is marked `aria-invalid="true"`.
3. Given a whitespace-only message, when the visitor submits, then the message field shows "Tell us a little about your project so we know who to put on the call".
4. Given only one field is invalid, when the visitor submits, then the summary names one problem.
5. Given the summary is shown, when the visitor activates a summary link, then focus moves to that field.
6. Given a field showing an error, when the visitor corrects it, then its error clears without a further submit.
7. Given a message over 2000 characters, when the visitor submits, then the message field shows an error stating the limit and no request is sent.

---

## L2-005: Sending state
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given a valid form, when the visitor submits and the request has not completed after 300 ms, then the button reads "Sending…", is marked busy, and the fields become read-only with their values unchanged.
2. Given the request is in flight, when the visitor activates the button again, then no second request is sent.
3. Given the request completes within 300 ms, when the result arrives, then the sending state is not shown.

---

## L2-006: Sent state
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given a valid submission, when the server accepts it, then the form is removed from the page and a confirmation titled "Request sent." appears stating that Goodwork will reply to the submitted email address within two business days, and focus moves to the confirmation.
2. Given the confirmation, when the visitor activates "Send another request", then an empty form is shown in the default state.

---

## L2-007: Error state
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given a valid submission, when the server responds with a 5xx status or the network fails or 15 seconds pass without a response, then an alert titled "We couldn't send your request" appears, receives focus, and offers the studio email as a `mailto:` link.
2. Given the error state, when the visitor views the form, then both fields keep what they typed and the button reads "Try again".
3. Given the error state, when the visitor activates "Try again" and the server accepts, then the sent state is shown.
4. Given a valid submission, when the server responds 400 with field errors, then those errors are shown as in L2-004.

---

## L2-008: Contact request endpoint
**Traces to:** L1-003

`POST /api/contact-requests` accepts `{ email, message }`. It is the only anonymous endpoint and is opted into explicitly.

**Acceptance Criteria:**
1. Given a valid body, when it is posted, then the API returns 202 and the request is stored with its email, message, UTC received time and a generated id.
2. Given an invalid email, an empty message, a message over 2000 characters, an email over 254 characters or a missing field, when it is posted, then the API returns 400 with a validation problem naming each invalid field, and nothing is stored.
3. Given extra unknown properties, when posted, then they are ignored and not stored.
4. Given surrounding whitespace in either field, when stored, then it is trimmed.

---

## L2-009: Delivery to the studio inbox
**Traces to:** L1-003

**Acceptance Criteria:**
1. Given a stored request, when it is accepted, then a notification email containing the sender's email and message is sent to the configured studio inbox with Reply-To set to the sender's address.
2. Given the mail service fails, when the request is accepted, then the request remains stored, delivery is retried, and the failure is logged without the message body.
3. Given the request cannot be stored, when it is posted, then the API returns 503 and the client shows the error state.
4. Given the studio inbox address, when the app starts, then it is read from configuration, never from source.

---

## L2-010: Abuse protection
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given one client address, when it posts more than 5 contact requests within 10 minutes, then further requests return 429 with a `Retry-After` header until the window passes.
2. Given the form contains a hidden honeypot field, when a submission fills it, then the API returns 202 but stores and delivers nothing.
3. Given a body larger than 16 KB, when posted, then the API returns 413.
4. Given a message containing HTML or script, when it is stored, emailed or rendered, then it is treated as plain text and never executed or interpreted as markup.

---

## L2-011: Transport and data protection
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given an HTTP request, when it reaches the site, then it is redirected to HTTPS and responses carry HSTS.
2. Given any response, when its headers are read, then it includes a Content-Security-Policy that disallows inline script, `X-Content-Type-Options: nosniff`, and `Referrer-Policy: strict-origin-when-cross-origin`.
3. Given application logs, when a contact request is processed, then the message body is never logged and the email address is not logged in full.
4. Given a cross-origin POST from another site, when it reaches the endpoint, then it is rejected by the CORS policy.
5. Given stored contact requests, when they are older than 24 months, then they are deleted.

---

## L2-012: Responsive layout
**Traces to:** L1-005

**Acceptance Criteria:**
1. Given a viewport under 576px, when the page renders, then sections and service cards stack in one column, nothing scrolls horizontally, and every target is at least 24×24 CSS px.
2. Given a viewport of 576px-767px, when the page renders, then content stays single-column with wider margins and no horizontal scroll.
3. Given a viewport of 768px-991px, when the page renders, then the two service cards sit side by side.
4. Given a viewport of 992px-1199px or 1200px and wider, when the page renders, then the layout matches the desktop mock, and at 1280×800 the whole page is no taller than 1100px in the default state.
5. Given text zoomed to 200%, when the page renders at 1280px, then no content is clipped or overlapping.

---

## L2-013: Light and dark themes
**Traces to:** L1-005

**Acceptance Criteria:**
1. Given the operating system prefers dark, when the page loads, then it renders the dark theme (evergreen ink canvas, linen text, gold accent) with no flash of the light theme.
2. Given the operating system prefers light or states no preference, when the page loads, then it renders the light theme.
3. Given either theme, when colours are measured, then every text and control pair meets WCAG 2.2 AA contrast.

---

## L2-014: Accessibility
**Traces to:** L1-006

**Acceptance Criteria:**
1. Given each of the five states, when an axe scan runs, then it reports no violations.
2. Given a keyboard-only user, when they tab through the page, then every interactive element is reachable in visual order and has a visible focus indicator.
3. Given a screen reader, when the error summary, sent confirmation or error alert appears, then it is announced.
4. Given the page structure, when headings are read, then there is one `h1` and headings do not skip levels.
5. Given a user who prefers reduced motion, when "Start a project" is activated, then the page jumps without animated scrolling.

---

## L2-015: Front-end performance
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given a production build on an emulated mid-range phone over a 4G connection, when the home page loads, then Largest Contentful Paint is under 2.5 s, Cumulative Layout Shift under 0.1 and Interaction to Next Paint under 200 ms.
2. Given the production build, when the initial JavaScript is measured, then it is under 200 KB compressed.
3. Given the page's fonts, when it loads, then Inter and Source Serif 4 are self-hosted and use `font-display: swap`; no request goes to a third-party font host.

---

## L2-016: Endpoint performance
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given 20 concurrent valid submissions, when they are posted, then the 95th percentile response time is under 500 ms, and email delivery happens off the request path.
